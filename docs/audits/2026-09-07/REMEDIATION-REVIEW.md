### R01｜P1：T3.2 会破坏正常的 t-test 和 lm 调用

新 `prune_backend_args()` 只拒绝非 NULL 的不支持参数，最后却原样返回 `args`。现有 `run_diff()` 总是构造包含 `covariates = NULL`、`paired_col = NULL` 的参数列表；原函数还承担删除后端不接受的形参这一必要职责。

### R02｜P1：T1.1 封住列名解析后，仍可能建立错误的对比

位置：[方案第 103 行](/Users/puweilin/SciProject/CHISSS/omicsApp/docs/audits/2026-09-07/REMEDIATION-PLAN.md:103)、[前缀处理第 124 行](/Users/puweilin/SciProject/CHISSS/omicsApp/docs/audits/2026-09-07/REMEDIATION-PLAN.md:124)。

用内部名称建立公式是正确方向，但 `startsWith(cn, "v1")` 不是无歧义的字段映射，`v10` 也会命中。直接执行候选函数：一个分组列加九个协变量会产生列名 `A, B, v2, …, v9, 0`，随后 `makeContrasts()` 因非法名称 `0` 报错。

更严重的是**不报错而比较了错误系数**。当合法的两个组名为 `A`、`v2`，同时加入一个数值协变量，候选设计列名为：

```text
A | v2 | v2
实际 contrast 权重：-1 | 0 | 1
期望 contrast 权重：-1 | 1 | 0
```

组名与内部协变量列名相撞，当前 `makeContrasts(v2 - A, …)` 取到了协变量系数。结果可能仍是完整表和正常图，但统计比较已经错误。

**修订要求：** 公式项、设计矩阵列、用户显示标签分别管理。设计矩阵最终列名也必须唯一且由程序生成，基于明确的系数位置构造数值 contrast；用户标签只进入显示映射。不要再通过字符串剥前缀或 `make.names()` 猜测系数对应关系。

连续变量、样条、ANOVA 的替换也要明确列映射、缺失值处理、矩阵秩、自由度和检验对象。`lm.fit()` 不能仅凭一句“同理”直接代替现有 `lm()` 周边逻辑。

**验收：** 增加组名 `v2`、多协变量、含空格/中文/标点的组水平、`make.names()` 后相撞的标签、恶意协变量名及连续变量名；对照手工指定的安全矩阵与数值 contrast 比较结果。安全测试还要证明实际进入目标建模路径，不能只 `try()` 后检查 marker 未出现。

### R03｜P1：T2 的单一 QC 槽位不能支撑多组学；整合第二层仍绕过 QC

位置：[“不需要新结构”第 439 行](/Users/puweilin/SciProject/CHISSS/omicsApp/docs/audits/2026-09-07/REMEDIATION-PLAN.md:439)、[清洗输入选择第 612 行](/Users/puweilin/SciProject/CHISSS/omicsApp/docs/audits/2026-09-07/REMEDIATION-PLAN.md:612)、[整合不需修改第 642 行](/Users/puweilin/SciProject/CHISSS/omicsApp/docs/audits/2026-09-07/REMEDIATION-PLAN.md:642)。

方案保留 `experiments[[tag]]`，把清洗结果放在 `bundles$qc`，这只能保存一个层的已应用 QC。先对蛋白组应用，再对 RNA 层应用，后者会替换前者；重新分析蛋白组时，层标签不匹配，T2.2 会回退到导入层。

加 `layer_tag` 可以避免错误匹配，却不能保存两个层的清洗状态。这里的 `experiments` 是导入后的层，可能已经归一化，不应与原始强度混为一谈。

“整合模块不需要改——它们吃的是 diff bundle”不符合当前实现：

- [mod_integration_view.R:82](/Users/puweilin/SciProject/CHISSS/omicsApp/packages/omicsApp/R/mod_integration_view.R:82) 从 `proj$experiments` 直接取第二层。
- [mod_integration_view.R:224](/Users/puweilin/SciProject/CHISSS/omicsApp/packages/omicsApp/R/mod_integration_view.R:224) 用这一层重新运行差异分析。
- T3.2 只新增协变量与配对参数继承，没有改变第二层的数据来源。

因此，按当前方案会继续出现“第一层使用清洗数据，第二层使用导入数据”的结果。

**修订要求：** 引入按层保存的已应用预处理状态，例如 `preprocessing[[tag]]`，或者等价的按层 QC 索引。具体名称可由实现决定，但必须同时容纳各层的清洗数据、解析后参数、输入版本和处理记录。差异分析、整合中的第二层差异分析、报告和脚本应复用同一个有效输入解析函数。

**验收：** 两个层都制造可识别的待过滤特征/样本，分别应用不同 QC，反复切层、保存、重启、恢复，再运行两层差异与整合。逐层断言实际输入矩阵、ID 集、样本数、特征数与已提交状态一致。

### R04｜P1：T3.4 写入 provenance 的位置与导出读取位置不一致

位置：[写入位置第 1163 行](/Users/puweilin/SciProject/CHISSS/omicsApp/docs/audits/2026-09-07/REMEDIATION-PLAN.md:1163)、[权威源说明第 1177 行](/Users/puweilin/SciProject/CHISSS/omicsApp/docs/audits/2026-09-07/REMEDIATION-PLAN.md:1177)、[导出循环第 1239 行](/Users/puweilin/SciProject/CHISSS/omicsApp/docs/audits/2026-09-07/REMEDIATION-PLAN.md:1239)。

T2 明确不将清洗数据写回 `experiments`；T3.4 将 QC 步骤追加到 `cleaned_input$provenance`，但导出却遍历 `experiments[[tag]]$provenance`。按这份数据契约构造对象，导出读取侧仍没有 `run_qc` 步骤。归一化可能补齐了，QC 复现仍会遗漏。

“`bundles$qc` 被清掉，但数据却还在”的理由也不成立：按 T2 的存储约定，清洗数据及其 QC provenance 正是在这个 bundle 中。删除唯一引用的槽位，就失去了项目持久化中的那份数据和处理记录。

**修订要求：** 与 R03 一起定义持久化结构和读取合同；导出应沿着结果所引用的有效输入版本重放，而不是拿当前导入层的处理记录猜测历史结果。明确不同步骤返回值的取法：`read_omics()` 返回 `$input`，`run_qc()` 返回 bundle 中的 `$results$cleaned_input`，不能将所有操作无差别串成同一种赋值。

补齐源文件归档路径的重定位、摘要验证、`sheet_roles`、实际默认参数、随机种子/相关实现版本、两个差异 bundle、sample link 与基因集版本。`normalize_omics()` 目前的形参是 `input, method, offset`，没有方案所说的 `...`；应明确记录 `offset`。

旧项目缺少处理记录时，不应继续声称“复现分析但不复现导入”，因为已知遗漏归一化会改变分析数值。若无法重建处理历史，应禁用完整复现导出，或生成明确停止执行、要求补充信息的草稿。

**验收：** 在独立目录从归档原文件执行导出脚本，核对中间矩阵、特征/样本 ID、参数、最终 effect、statistic、P 值、校正 P 值与整合结果。先按稳定键对齐后比较；不仅检查 effect 向量。没有 provenance 的旧项目应有明确的降级测试。

### R05｜P1：QC 应用可以把旧预览贴上当前层身份；控件恢复也未解决

位置：[应用处理第 471 行](/Users/puweilin/SciProject/CHISSS/omicsApp/docs/audits/2026-09-07/REMEDIATION-PLAN.md:471)、[控件选择第 540 行](/Users/puweilin/SciProject/CHISSS/omicsApp/docs/audits/2026-09-07/REMEDIATION-PLAN.md:540)。

当前 [mod_qc_view.R:238](/Users/puweilin/SciProject/CHISSS/omicsApp/packages/omicsApp/R/mod_qc_view.R:238) 在 QC 失败时保留上一次成功的 `last_bundle`。方案的应用按钮只检查 `b` 和当前层存在，就把**当前**层的标签、指纹写入旧 `b`。层选择本身也不等于底层数据被替换，不一定触发 `layer_generation`。

可达场景：A 层预览成功；切换 B 层，新预览因阈值过严失败；点击应用。按候选提交逻辑，结果成为 `B | fp-B | from-A`。即使不切层，新参数失败后也可能提交旧参数的预览。显示旧图作为参考可以保留，但旧预览不能被当作当前请求的成功产物提交。

此外，实际执行方案中的 Shiny 恢复规则：已有合法选择 `knn` 时，打开保存为 `min` 的状态，仍选中 `knn`。因为当前 input 优先于保存参数，正是方案希望消除的设置错配。

**修订要求：** 预览启动时捕获项目激活版本、层版本和参数签名，并将它们保存到预览结果。应用时验证预览成功且签名仍匹配；不能在应用阶段重新给旧结果签发身份。项目/层激活时执行一次明确的控件恢复，再允许用户编辑草稿；保存参数、草稿参数、已应用状态分开显示。

**验收：** 覆盖“成功后失败再应用”“切层后预览失败再应用”“A 项目 knn → B 项目 min”“已保存方法在当前环境不可用”；前两种必须拒绝提交，后两种不能静默选另一个方法。

### R06｜P1：T2.3 只清视图，不足以清除项目中已保存的旧分析

位置：[方案第 695 行](/Users/puweilin/SciProject/CHISSS/omicsApp/docs/audits/2026-09-07/REMEDIATION-PLAN.md:695)，以及 [app_server.R:180](/Users/puweilin/SciProject/CHISSS/omicsApp/packages/omicsApp/R/app_server.R:180)。

`downstream_generation` 分开设计是合理的。但当前回写 observer 仅在某视图**此前持有非空 bundle**、且 generation 条件满足时，才删除项目中的相应 bundle。

恢复一个磁盘项目时，项目可以含有 saved diff，而对应视图为空。此后改变并应用 QC，仅让视图继续返回 NULL，不会删除项目原有 diff。直接执行当前回写片段，这种状态下 `SAVED_DIFF_RETAINED_WITH_EMPTY_VIEW=TRUE`。报告、保存与导出读取项目，仍可拿到旧结果。

另一个问题是 `qc_identity` 只比较原始层标签/指纹和 params；方案仍用矩阵形状作为无指纹输入的身份。两个不同的 20×10 矩阵会得到同一身份。记录 provenance 或修好缺失参数后，也不能把“同形状”当作“同数据”。

**修订要求：** 提交 QC 时，在项目事实状态中明确使所有依赖它的结果失效或移出当前有效结果集合，视图同步这个状态。不能仅依赖 observer 顺序和曾经显示过什么。结果应引用输入版本；旧结果若保留为历史，也必须不能被当前报告当作有效结果。无上传摘要的输入使用内容摘要或明确的不可变版本 ID。

**验收：** 在“运行中的项目”和“刚从磁盘恢复、尚未打开分析页面的项目”两种状态改变 QC；同时检查内存项目、视图、autosave、重启恢复和导出。仅断言页面 bundle 为 NULL 不够。

### R07｜P1：T2.4 的 project_id 不能代表一次打开/恢复操作

位置：[身份生成第 789 行](/Users/puweilin/SciProject/CHISSS/omicsApp/docs/audits/2026-09-07/REMEDIATION-PLAN.md:789)、[切换判断第 808 行](/Users/puweilin/SciProject/CHISSS/omicsApp/docs/audits/2026-09-07/REMEDIATION-PLAN.md:808)、[归属检查第 824 行](/Users/puweilin/SciProject/CHISSS/omicsApp/docs/audits/2026-09-07/REMEDIATION-PLAN.md:824)。

增加持久化项目 ID 是必要的，但有两个确定的缺口：

1. 用户打开同一项目较早保存的版本，`project_id` 和原始数据都未改变，新 observer 不清空视图。当前内存里的新对比结果仍可能回写覆盖刚打开的旧结果。这里需要识别“激活了一个保存状态”，不只是“换了项目身份”。
2. `v$input_info$project_id %||% pid` 把无归属结果直接视为当前项目结果。这条检查实际允许未知归属，无法作为防止张冠李戴的兜底。

还需说明首次真实项目进入、关闭到 demo、再打开、另存副本、旧 `.omp` 迁移和控件/结果恢复的语义。用 `sample()` 生成 ID 会消耗分析用的随机流，并会在相同 `set.seed()` 状态下重复；应使用不依赖分析 RNG 的标识机制。

**修订要求：** 持久化 `project_id` 与每次打开/恢复递增的激活版本分别管理。每个新计算结果保存项目、激活版本、输入版本和任务序号；回写必须明确匹配。旧结果只能在明确的文件恢复流程中迁移和绑定，不能在通用回写中用当前身份填空。

**验收：** 除 A→B 相同数据外，必须增加“同一 project_id 重开旧保存”“另存副本”“无归属视图结果”“有归属的旧项目迁移”四类测试。

### R08｜P2：T1.4 的尺度修复需要完整的效果量合同

位置：[方案第 382 行](/Users/puweilin/SciProject/CHISSS/omicsApp/docs/audits/2026-09-07/REMEDIATION-PLAN.md:382)、[效果量标签第 404 行](/Users/puweilin/SciProject/CHISSS/omicsApp/docs/audits/2026-09-07/REMEDIATION-PLAN.md:404)。

补充三个容易被遗漏的边界：

1. **整合统计口径必须定下来。** Fisher 经典校准要求零假设下输入 P 值独立且均匀；不能仅通过产品选择把校正后 P 当作等价输入。来源：[SciPy 官方 combine_pvalues 文档](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.combine_pvalues.html)。对同一批受试者的两层组学，不能未经验证就假定满足独立性；这不等于本轮已经证明其错误率膨胀。若暂时没有经验证的合并检验方案，可先提供描述性一致性和分层显著性，关闭未经验证的合并显著性结论。保留时应明确检验假设、方向、缺失/零 P 值处理和校正范围，并取得验证证据。
2. **`is_significant` 拆列必须贯通消费者。** T3.1 改为两种显著性标记时，需要同步 schema、空结果、图表、过滤、报告和旧 `.omp` 读取；只加两列仍可能让旧消费者继续使用含义不清的原字段。实际保存的是 raw P 还是 adjusted P，也不能仅靠 `p_a/p_b` 名称猜测。
3. **部署排除项应覆盖真正的秘密文件。** `.dockerignore` 不能只补 `host.env.template`，还应检查实际生成的 `host.env`、`.env`、Keycloak 配置与密钥来源是否进入构建上下文。这里不声称它们已经被复制进最终镜像；“构建上下文包含”和“镜像内包含”应分别验证。

## 3. 建议的修订顺序与验收矩阵

先完成独立的入口修复：RDS、路径、归一化失败中止，以及安全且数值正确的设计矩阵/contrast。与此同时，先在方案中统一下面这条数据合同，再实施 QC、切换、恢复与脚本：

```text
项目身份 + 激活版本
  └─ 每层导入数据与版本
       ├─ QC 草稿/预览（独立，不直接影响分析）
       └─ 每层已应用 QC / 有效输入版本 / provenance
            └─ 引用该版本的差异分析
                 ├─ 富集
                 └─ 引用两层有效分析版本的整合

保存、恢复、报告、导出脚本都读取这一套明确归属的状态。
```

这是必要的接口设计，不要求一次重写整个应用。可以保留现有原始层与 bundle 对象，但不能继续把唯一的全局 QC 视图结果同时当作多层持久化事实。

| 必须覆盖的场景 | 关键断言 |
|---|---|
| 正常与恶意列名，多个后端/分析类型 | 无副作用，合法输入有有效结果；contrast、P 值与安全参考模型吻合 |
| 不支持参数缺省、NULL、实际值 | 前两者成功，实际不支持值拒绝；支持值确实影响拟合 |
| 两层分别提交 QC，往返切层 | 两层已应用数据都保留，主/次层差异与整合使用正确版本 |
| 预览失败后应用、切层后失败 | 不给旧预览重新绑定新身份，不提交错误版本 |
| 已保存项目在已有会话中恢复 | 四个 QC 控件、已应用数据、结果归属一致，不被当前草稿覆盖 |
| 恢复后改变 QC | 项目、视图、autosave、重启后状态、报告、脚本一致失效 |
| 同数据不同项目，以及同项目重开旧保存 | 无串写；打开的保存状态确实生效 |
| 完整导出脚本独立重放 | 中间矩阵与最终关键数值吻合；旧项目缺记录时明确停止或降级 |
| 异步成功/失败到达时版本已过期 | 两类回调均不能覆盖当前状态，不更新错误的保存状态 |
| 正式镜像与目标服务器 | 多账号隔离、目标并发资源、备份恢复、日志留存、升级回滚均有证据 |

验收应有测试 ID、对应问题、使用 fixture、执行环境、预期数值/状态、结果日志和发布 digest。对确定的代码缺陷，先验证测试在基线上暴露问题，再验证修复后通过；对于新增能力或关闭功能，用适用的正反向契约测试，不机械要求所有运维流程都套用单元测试“先红后绿”。

**建议给 Claude Code 的反馈：保留当前问题清单和主要整改方向，先修订 R01–R10，重点统一按层 QC、结果版本、项目激活和 provenance 的读写合同；完成上述场景的明确验收定义后，再将方案标记为可执行。正式部署需另外取得最终镜像和目标服务器的放行证据。**
